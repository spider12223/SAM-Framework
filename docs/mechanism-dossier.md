# S.A.M mechanism dossier

Code that looks wrong and is deliberately right. Written by the 2026-09 full audit so nobody "cleans" these into breakage.

## MainMenu.cpp

- **12001-12009** (loader): The host-side 'SAMF' handler passes a client-supplied byte (net_packet->data[4]) straight to SAMSync::sendFingerprint as a player slot. This is safe by construction, not by luck, and the reasoning should stay documented: the length guard prevents reading data[4] out of a short packet, sendFingerprint itself rejects slot <= 0 or >= MAXPLAYERS and disconnected slots (sam_sync.cpp:200-203) before indexing net_clients[player-1], and the payload is the host's own fingerprint — identical for every client — so a mis-targeted request only sends a benign packet that the receiver dedups. There is no OOB index and no information leak to add a check for.

## actmonster.cpp

- **420-443** (races): playerRaceCheckHostility computes vanilla `accepted` first, then lets a declared race allegiance overwrite it, and only then falls into the `if (!accepted)` MONOCLE arm. The ordering is the whole point: a race that declares shopkeepers hostile is still allowed to disguise with a monocle exactly as a monster race is, and a race that declares them friendly does not become immune to the wanted level (isPlayerEnemy at 404-417 still consults `h->wantedLevel` afterwards). Hoisting the S.A.M block below the monocle check, or making it `return` directly, would break both properties.

## actplayer.cpp

- **15586-15606** (races): The S.A.M limb override sits at the TOP of setDefaultPlayerModel and returns early, which is safe only because the function's entire body does nothing but assign `this->sprite` (verified through to its close at actplayer.cpp:16101). The guard `(int)playerRace == SAMRaces::hostMonsterForRace(stats[playernum]->playerRace)` looks redundant next to the `playerRace >= SAM_RACE_ID_BASE` test but is not: `playerRace` here is the body being DRAWN, so a polymorphed or shapeshifted player fails the comparison and keeps the shape they were turned into instead of snapping back to the race's custom limbs. Reaching this function at all already means the matching armour slot is empty (every caller checks), which is why the override belongs here and not at the draw site.

## draw.cpp

- **2108-2122** (engine-noop): The `if (SAMBodies::modelForEntity(entity) < 0) { continue; }` that un-skips an INVISIBLE entity looks like it inverts vanilla invisibility, and it does not. Six vanilla monsters (bat, duck, mimic, moth, sentrybot, summons) hide their MAIN entity because it is only an AI bodypart and all the art lives in the limbs; a mod-declared custom body is drawn ON that main entity while its limbs are hidden, so without this arm the creature is invisible from every angle. modelForEntity returns -1 immediately when no mod declares a body (sam_bodies.cpp:92-95: one bool and one empty() test), so the `continue` still fires for every vanilla invisible entity. The whole arm sits inside #ifndef EDITOR because editor.exe links draw.cpp but NOT sam_bodies.cpp (it is GAME_SOURCES only, CMakeLists.txt:145) — removing that fence breaks the editor link, not the game.

## entity.cpp

- **1618-1641** (effects-spells): The custom-effect per-second arm inside Entity::effectTimes re-asserts a custom effect's `grants` flags (setEffect(gf, true, TICKS_PER_SECOND * 3, true)) from INSIDE the very `for (c = 0; c < NUMEFFECTS; ++c)` loop that is decrementing those same timers. That is safe only because of an ordering invariant that is easy to destroy: the allowlist in samGrantFlagToSlot (sam_effects.cpp:29-37) admits only LEVITATING/INVISIBLE/TELEPATH, all far below SAM_EFFECT_SLOT_BASE=135, so slot gf has already been processed earlier in this same pass by the time the custom slot c >= 135 rewrites its timer. The 3-second window against a ~1/second refresh is also deliberate: a shorter window could let the flag lapse to 0 between refreshes and fire a spurious on_effect_removed/on_effect_applied pair. Widening the allowlist to a flag with an id >= 135, or moving this arm before the loop, breaks both properties.
- **19898-19923 and 20505-20531** (races): The two S.A.M allegiance arms sit at the very END of the vanilla per-race switch, still inside the `if (!foundFollower)` branch, and this position is exact. Earlier and the host body's own relations would overwrite the race's declaration; later (past the mask block at 19924+ in checkEnemy, or outside the leader/follower structure) and masks, confusion, leaders and follower lists would stop being able to override it — which is the precedence a vanilla race gets. The two functions are mirrors: checkEnemy writes `result = (samRel == 0)` and checkFriend writes `result = (samRel == 1)`. They must be edited together, or a monster will refuse to attack something it also refuses to help. The SHOPKEEPER exclusion in both is not an oversight — shopkeeper disposition is routed to playerRaceCheckHostility so the wanted level stays the single authority.
- **94-125** (engine-noop): `static ClassHPMPValues samRow;` inside ClassBaseGrowths::getClassBaseGrowths returns a reference to a function-local static that is overwritten on every custom-class call. That is safe here and only here: all three callers (entity.cpp:4792, 27745, 27856) bind the reference and read it immediately for a single player, never holding two rows at once, and unlike a cache it cannot go stale across a /sam_reload because it is rebuilt from the registry on each call. The alternative — indexing classBaseGrowths with a custom id >= 1000 — is what this replaced: it silently routed every custom class to the "default" row at index 0, so every custom class ever published shared identical HP/MP growth and regen no matter what its JSON declared.

## init.cpp

- **767-785** (engine-noop): The #ifdef EDITOR block (modelFileNames[c] = filename) and the #ifndef EDITOR block (SAMModels::noteVanillaModelPath(c, name)) do the same job for the two targets and neither fence is removable. The game build historically read the model name, loaded the voxel and threw the name away — it was only kept under EDITOR — so keeping it is what lets a mod write "gharbad_head.vox" instead of the literal index 1025. The guard is not stylistic: editor.exe links init.cpp but not sam_models.cpp (CMakeLists.txt:144 marks it game-only, needing GL generateVBOs), so an unguarded call is an editor link error. This exact class of break has bitten this project twice; the same fence pattern protects draw.cpp:2110 and opengl.cpp:1316/1435/1448.
- **778-784** (races): The `SAMModels::noteVanillaModelPath(c, name)` call is wrapped in `#ifndef EDITOR` and that guard is mandatory, not cosmetic. init.cpp is listed in EDITOR_SOURCES (src/CMakeLists.txt) but sam_models.cpp is game-only ("custom .vox models — game only (needs GL: generateVBOs)"), so an unguarded call breaks the editor link. It sits in the `#else` of the existing `#ifdef EDITOR` modelFileNames block because the editor already keeps the same names for its own purposes; the game build was throwing them away, which is the only reason a mod had to write "1025" instead of "gharbad_head.vox".

## items.cpp

- **743-806** (engine-noop): The modded-loot arm is split across itemLevelCurve in a way that must stay split. SAMItems::lootCandidates is asked for eligible ids BEFORE the `numoftype == 0` bail (so a category with only modded items still works), the count is folded into `numleft` before the single `rng.rand() % numleft`, and the modded pick is resolved only AFTER the vanilla walk has exhausted `pick`. That ordering is what makes a seeded vanilla run byte-identical: with no mod the vector is empty, numleft is unchanged, no extra rng.rand() is consumed anywhere, and the `if (pick < samCandidates.size())` tail at 802 is unreachable. Note also that lootCandidates reads the LIVE items[id] slot rather than the parsed def (sam_items.cpp:1108-1114), because reapplyAfterDataReload re-stamps those fields and a sam_patch_item may have changed the level after load.

## maps.cpp

- **1567-1590** (engine-noop): Room injection sits between the sublevel-scan loop and everything downstream, and cannot be moved. The loop above has just finalised `numlevels`, and `possiblerooms` is not allocated until much later (it is sized from numlevels), so growing numlevels here is picked up automatically by every later step; do it anywhere else and either the pool or the allocation is wrong. The `numlevels >= 100` break is not defensive padding — the sublevel index space is a fixed 0..99. The ordering of SAMRooms::roomsFor() is the real invariant (sam_rooms.cpp:90-97): the list is sorted by (namespace, path), never by mod load order, because the picker does `map_rng.rand() % numlevels` and in multiplayer every client regenerates the map itself from a shared seed — an order that differed between machines would put two players in different dungeons with nothing reporting a problem.

- **9707-9724** (engine-noop): `if ( !wasLoadingSaveGame ) { SAMWorldState::clearAll(); }` in doNewGame reads a COPY of loadingsavegame captured earlier in the function, not the live global, and that is the whole point: loadingsavegame is already 0 by this line, so gating on it would clear the state loadGame() just restored. doNewGame is also the only correct home for this — doEndgame is skipped on both the die-and-restart and host-restarts-lobby routes to a fresh character. ## net.cpp

- **1646-1760** (engine-net-save): The 32-bit class id is APPENDED as a tail (JOIN: SDLNet_Write32 at data[41], len 45; HELO: samWriteClassTail at offset 8 + MAXPLAYERS*chunk_size) instead of widening the in-chunk single byte at data[5] / chunk+2. That is deliberate wire compatibility: widening in place would shift `sex`, `appearance`, `race` and `name` for every peer on an older build. The one-byte fields are still written with the truncated value on purpose, and every reader gates the tail on packet length (ui/MainMenu.cpp:12270-12277 checks `len >= 45`; ui/MainMenu.cpp:12723-12727 checks `len >= samTail + MAXPLAYERS*4`; net.cpp:6652 and 9478 check `len >= 13` for 'ASSC'), falling back to the old byte rather than reading past the packet. Sizes stay inside NET_PACKET_SIZE (512): the largest case is the loadingsavegame HELO at 8 + 4*98 = 400 bytes plus a 16-byte tail = 416. Do not 'clean up' the redundant byte writes or drop the length guards.
- **5287-5317** (engine-noop): The 'SAMI' overlay handler is registered only in clientPacketHandlers (the table starting at net.cpp:2698), never in serverPacketHandlers — that asymmetry is the security property, not an oversight: the host never accepts one, so no client can put a full-screen picture on another player's display. Every length is re-derived from the packet rather than trusted: `net_packet->len < 20` first, then nsLen/nameLen each bounded against SAMImages::SAM_IMAGE_MAX_NS/NAME, then the combined `len < 20 + nsLen + nameLen` check before the two std::string constructions read from data[20]. The player index is clamped with std::min against MAXPLAYERS-1. Removing any one of these turns a lying length byte into an out-of-bounds read. The design of sending the NAME and re-resolving it locally (sam_images.cpp:applyRemote) rather than sending pixels is also deliberate: a client missing the mod draws nothing instead of desyncing, and the payload fits a datagram.
- **7206-7218** (engine-net-save): The `samVariations` guard in the server 'ITMU' handler must stay. entity->skill[10] is a ground item's type read straight off the entity, and a save carrying a custom item whose mod has been removed lands on an unregistered slot whose `variations` is 0. Clients auto-request ITMU every few seconds with no player input, so the original unguarded `entity->skill[14] % items[...].variations` was a divide-by-zero that killed the HOST and took the whole session down. The bounds check is against NUM_ITEM_SLOTS (6064), not NUMITEMS, because custom item ids legitimately live at 5000+.

## opengl.cpp

## sam_backup.cpp

- **150-159** (world): Deleting the just-created folder when zero files copied is required by the once-per-day guard, which keys on a folder NAME starting with today's date (lines 108-120) and not on whether that folder has any contents in it. Leaving an empty today-dated folder behind would make every later backup attempt that day return early, silently disabling the safety net for the rest of the session. Relatedly, the prune at lines 163-186 sorts folder names lexicographically and relies on the "%Y-%m-%d_%H-%M-%S" stamp from nowStamps() being fixed-width and zero-padded, which makes lexicographic order equal chronological order — changing the stamp format would silently break the prune's oldest-first assumption.
- **71-76, 189-206** (world): backupImpl is split out purely so backupIfNeeded can wrap it in try/catch, and the comment's reasoning is correct and non-obvious: the error_code overload of std::filesystem::directory_iterator makes only CONSTRUCTION non-throwing — the range-for's operator++ is the throwing one, so a mid-scan OS error (a removable drive vanishing, a permission change) would escape into mod loading. The header's contract is that a failed backup must never block loading, and this try/catch plus the catch(...) is what enforces it. Do not collapse the two functions back together or drop the catch-all.

## sam_bodies.cpp

- **104-108** (monsters): The death-gib body tag genuinely cannot be a uid map and the +1 offsets and the sprite comparison are all load-bearing. spawnGib (actgib.cpp:1073-1079) tags the gib on the entity itself because a few lines later the gib does `entity_uids--` then `setUID(-3)` (actgib.cpp:1105-1108): every gib in the game shares uid 0xFFFFFFFD, AND the uid it gave up is handed straight to the next entity created, so a uid-keyed tag would both miss the gib and be inherited by an unrelated entity. skill[57]/[58] are safe slots (NUMENTITYSKILLS is 60, entity_shared.cpp:473-476 zeroes the whole array, and no act* behaviour touches indices this high). Storing both values +1 is what makes 0 a usable "untagged" sentinel. The `entity->sprite == entity->skill[58] - 1` test is not redundant: at the moment spawnGib runs, the body gib and the blood gibs spawned beside it are identical; the 13 vanilla *Die functions stamp `gib->sprite = my->sprite` on the body gib only AFTER spawnGib returns, so comparing the recorded parent sprite at draw time is the only way to tell them apart. Do not 'simplify' this into a uid lookup or drop the sprite check.
- **105-112** (engine-noop): `if (entity->skill[57] > 0) return (entity->sprite == entity->skill[58] - 1) ? (entity->skill[57] - 1) : -1;` is the death-gib path and the +1 offsets are intentional. Gibs all share uid -3, so they cannot be keyed by uid like every other entity here; the *Die function stamps the body tag onto the gib itself as skill[57] = modelIndex + 1 and skill[58] = parentSprite + 1, using +1 so that 0 stays a usable "not tagged" sentinel (model index 0 is a real model, models/system/null.vox). The sprite comparison is what separates the one gib carrying the parent's shape from the blood gibs spawned alongside it, which keep sprite 5/211 and correctly fall through to -1.
- **117-141** (monsters): The limb-hiding test must stay `entity->parent != 0 && entity->behavior != &actMonster && entity->skill[2] == (Sint32)entity->parent`, and it must return 0 rather than -1. 'Has a parent' alone is wrong: castSpell, arrows, thrown weapons and the devil's boulders all stamp the launcher's uid onto `parent`, so a parent-only test would make a custom-bodied dragon breathe invisible fireballs. skill[2] is the real limb marker — every limb in the 41 monster_*.cpp files is built with `entity->skill[2] = my->getUID()` right beside `my->bodyparts.push_back(entity)`, and projectiles never set it (Entity's constructor leaves skill[2] at -1, entity_shared.cpp:481, which cannot collide with a real parent uid). Returning 0 is deliberate: glDrawVoxel bails on models[0] (opengl.cpp:1338-1341), so 0 is the engine's own 'do not draw'. The deliberate absence of recursion/uidToEntity is also correct — one frame of a stray limb at spawn is cheaper than reaching into the entity list from inside the renderer.
- **118-141** (engine-noop): The limb-hiding test is `entity->parent != 0 && entity->behavior != &actMonster && entity->skill[2] == (Sint32)entity->parent`, not the obvious `entity->parent != 0`. Do not simplify it. A monster stamps its own uid into `parent` on everything it LAUNCHES too — castSpell sets missileEntity->parent, and so do arrows, thrown weapons and the devil's boulders — so hiding on `parent` alone would make a custom-bodied dragon breathe invisible fireballs. skill[2] is the real limb marker: every limb in the engine is built with `entity->skill[2] = my->getUID();` immediately next to `my->bodyparts.push_back(entity)`, a pairing that holds 1:1 across all 41 monster_*.cpp files, while projectiles leave skill[2] at 0. The deliberate absence of recursion / uidToEntity here is also load-bearing: if the parent has not resolved yet the limb simply draws for one frame, which is a far better trade than reaching into the entity list from inside the renderer.

## sam_classes.cpp

- **1096-1137** (classes): The body_model numeric branch rejects index 0 separately from out-of-range (lines 1115-1131). Index 0 is models/system/null.vox, the engine's empty model: it passes every bound check and then draws nothing, producing a success line in the log for a class that renders as literally invisible — harder to diagnose than silence. - **1184-1201** (classes): headSpriteFor resolves races[race] -> races["default"] -> -1 and returns -1 (leave the player alone) rather than falling back to some other race's entry. This asymmetry is required: Barony's limb-offset table is indexed BY RACE, so a head authored for a human placed on a goblin sits at the wrong focal point. - **1208-1234** (classes): applyManaRegen adds mpRegenBase, then per-stat scaling, then multiplies by mpRegenMultiplier — so a multiplier of 0 (or a large negative base) can drive regenPerMinute to zero or below, and the caller divides by it. Its position in charclass.cpp, after applyStatOverrides and the challenge-run block but BEFORE the HP/MP clamp and OLDHP recompute, is also deliberate so HP/MAXHP still normalise afterwards.
- **1255-1339** (classes): The non-local branch (1327-1332) intentionally does NOT mirror the local branch: it calls useItem() for equip-flagged items and simply free()s everything else. Likewise the guard on line 1264 duplicates the one the charclass.cpp hook already applies at charclass.cpp:756-759 — it is defence in depth against a future caller, not dead code to delete.

- **1341-1369** (classes): reapplyHotbarPins exists because Barony's ClassHotbarConfig_t::assignHotbarSlots (mod_tools.cpp:10056) runs several frames AFTER applyLoadout and zeroes/rebuilds the whole bar; the hook is at the very end of that function (mod_tools.cpp:10178) and must stay there. The inner loop that zeroes other slots holding the same uid (1361-1364) prevents a pinned item from appearing twice after the default-layout pass auto-placed it.
- **260-301** (classes): portraitPath/portraitSelectedPath are described as "absolute" in the comments and in ui/MainMenu.cpp:17758-17761, but joinPath(manifest.modPath, ...) actually produces a CWD-RELATIVE path ("./mods/foo/portrait.png") because Mods::mountedFilepaths are cwd-relative. - **65-74, 126-143, 188-206** (scripting-docs): setTile deliberately does NOT call generatePathMaps(); it only sets s_pathMapsDirty when the edited layer is OBSTACLELAYER, and connected() rebuilds once before it answers. ## sam_world_state.cpp

- **15-20, 154-171** (world): kModSetKey is the bare string "sam_modset", pointedly NOT under the "sam:" prefix, and absorb() tests `key == kModSetKey` BEFORE the prefix comparison. Both details are the collision guard: every mod key is written as "sam:" + ns + ":" + key (line 138-139) so no mod can ever produce the bare name, and checking it first means the prefix path never has to special-case it. The split rule is equally deliberate — namespaceUsable() forbids ':' in a namespace but keys may contain it freely, because absorb() splits on the FIRST separator at or after the prefix (`key.find(':', plen)`), so ns is unambiguous and the remainder, colons and all, is the key. Do not "tidy" kModSetKey under the prefix and do not reorder the two checks.
- **27-29, 128-135, 147-152** (engine-net-save): `kModSetKey` is "sam_modset", deliberately NOT under the "sam:<ns>:" prefix, and absorb() tests it BEFORE the prefix test. That ordering is what makes the key unforgeable by a mod: set() rejects any namespace containing ':' and every mod key is emitted with the "sam:" prefix, so no script-written key can ever collide with the mod-set record, and absorb() can never mistake the record for a mod's data. collect() also writes it unconditionally (even when no mod stored anything), because the point is to record which mod SET the save's content ids were allocated against — true whether or not a script used the world store.
- **73-92** (engine-net-save): set() computes `projected = totalBytes() + entryBytes(new)` and then SUBTRACTS the existing entry's bytes when the key is already present. The apparent double-accounting is intentional: it measures the total as it would be AFTER the write, so replacing a large value with a smaller one is never refused just because the current total is already near kMaxTotalBytes. entryBytes() (4 + ns + 1 + key + value) mirrors exactly what collect() emits into additional_data ("sam:" + ns + ":" + key, value), so the budget is measured in the units that actually land in the savegame.
- **77-94** (world): set() computes `projected = totalBytes() + entryBytes(ns, key, value)` and then SUBTRACTS the entry the key already occupies before comparing to kMaxTotalBytes. The subtraction looks redundant but is what makes replacing a large value with a smaller one always succeed once the store is near the 64 KB budget; without it a mod that had written a 6 KB blob could never shrink it. entryBytes' `4 + ns.size() + 1 + key.size() + v.size()` is the real on-disk shape of the pair (the "sam:" prefix, the namespace, the ':' separator, the key, the value), not an estimate.

## scores.cpp

- **7120-7131** (engine-net-save): `if ( this->char_class <= CLASS_MONK || this->char_class >= SAM_CLASS_ID_BASE ) return VALID_OK_CHARACTER;` in isCharacterValidFromDLC is a range check, deliberately NOT a SAMClasses::getClass() lookup. ## stat.cpp

- **1645-1657** (effects-spells): The SAM curable check in Stat::statusEffectRemovedByCureAilment sits ABOVE the switch rather than in a `default:` arm, which looks like sloppy placement. It is required: the switch ends in `default: break;` followed by `return false;`, so anything appended after it is unreachable. The guard `effect >= SAM_EFFECT_SLOT_BASE` means no vanilla case can be shadowed (no vanilla effect id reaches 135), making the arm purely additive false->true. /sam_curable proves this by running the real predicate twice per slot with SAMEffects::suppressCurableForTest toggled, plus EFF_POISONED/EFF_VAMPIRICAURA controls.
- **1646-1655** (engine-noop): The SAMEffects::isCurable check is at the TOP of Stat::statusEffectRemovedByCureAilment, above the big switch, and must stay there. The switch ends in `default: break;` followed by `return false;`, so anything appended after it would be unreachable — the natural place to add an arm is the one place that silently does nothing. Placement is safe in the other direction too: the arm only fires for slots >= SAM_EFFECT_SLOT_BASE (135), which no vanilla `case` covers, and it can only turn false into true, never the reverse, so no vanilla answer can change.
